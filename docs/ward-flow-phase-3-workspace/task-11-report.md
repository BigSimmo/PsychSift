## Access target — computation, labelling, isolation from `LegalForm`

`accessTargetLine(minutesInDepartment: number)` in `ed-screen.tsx` is the only place
`ED_ACCESS_TARGET_MINUTES` is used. Its **only** inputs are `now` and `movement.openedAt` (passed
in as a plain number, computed inline as `Math.max(now - movement.openedAt, 0)`); the function
never receives a `Movement`, never reads `movement.legalForm`, never constructs a `{code, label,
kind}` object, and never assigns anything to a `dueAt`. Wording is deliberately free of "due",
"deadline", "breach", "overdue" and "legal":

- Row label: **"Departmental access target"**.
- Row text: `"<Xh Ym> over the 4h 00m departmental access target"` or `"<Xh Ym> under the 4h 00m
departmental access target"`.
- The governance banner at the top of the screen states in full prose: _"The four-hour figure below
  is this department's own access target — a performance measure it is judged on, not a Mental
  Health Act deadline."_
- Styling: an over-target row colours in `--warning-text` (the same tone the rest of the app uses
  for an operational concern), deliberately **not** the `--danger-*` tone the two restriction
  notices elsewhere in Ward Flow use for a genuine legal concern — documented in `ed.module.css`'s
  comment on `.clockRow[data-state="over"]`.

`tests/ward-flow-single-source.test.ts`'s two static guards (the naive `{code,label,kind}` +
`ED_ACCESS_TARGET_MINUTES` co-occurrence check, and the `dueAt: ED_ACCESS_TARGET_MINUTES` direct-
assignment check) both pass against this file, confirmed by the 15-file/199-test node run below —
but per that file's own comment, those are a tripwire for the naive literal case, not proof. I
grepped `ed-screen.tsx` for every reference to `ED_ACCESS_TARGET_MINUTES` by hand (three: the
import, `accessTargetLine`'s subtraction, and one `data-state` attribute) and confirmed none is
anywhere near a `legalForm`/`dueAt` read or write.

## The two clocks

- **Time in department**: `elapsedLabel(movement, now)` (existing helper, `now - openedAt`).
- **Legal clock**: `legalClockReference(movement)` returns `formedAt` when `isCommunityFormed`
  (`formedAt !== undefined && formedAt < openedAt`), otherwise `openedAt` itself — so the two
  clocks read as _equal_ rather than diverging when there is nothing to diverge from, and the
  legal clock's reference point can only be earlier or equal to `openedAt`, never later. This
  makes "never renders shorter" a structural guarantee, not something that has to be separately
  checked per row.
- Rows carry `data-community-formed="true"` only when the two diverge, plus numeric
  `data-minutes-in-department` / `data-minutes-legal-clock` attributes (mirroring
  `pressure-strip.tsx`'s own `data-breaching`/`data-longest-minutes` convention) so tests assert
  the real sort/comparison keys rather than parsing prose.

## Handover control mirrors its reducer precondition

`handoverBlockedReason(movement)` in `ed-screen.tsx` is a direct mirror of
`ward-flow-reducer.ts`'s `case "HANDOVER_READY"`, which has exactly one guard:
`movement.stage !== "bed_held"`. The control uses `aria-disabled="true"` +
`onClick={ignoreUnavailableActivation}` + `title`/`aria-describedby` naming the movement's actual
stage when blocked — never native `disabled`, never both attributes together. `RAISE_REFERRAL` (no
reachable failure from this screen, since `edId` is always the page's own resolved department) and
`RECORD_EXAMINATION` (mirrored by `examinationBlockedReason`, checking `legalForm?.code !== "1A"`
and `movement.examination` already set, in the reducer's own order) get the same treatment.

## Test bug found and fixed (not a mutation — a real flake, diagnosed)

My "marks handover ready only once a bed is held" test reliably failed on the first two attempts
(once mid-full-suite, once running solo) with the click on `ward-ed-handover-WF-016` appearing to
do nothing — the outstanding item stayed `"handover"` across 22 retries over 10 seconds. I
reproduced this directly against the live app with a small script that mirrored the test's exact
navigation (`waitUntil: "domcontentloaded"`, no `waitForLoadState("networkidle")`) and confirmed
the click genuinely did nothing; the same script with a `networkidle` wait inserted worked
correctly (outstanding item became `"transport"` / `"Requested"` after the click). Diagnosis: the
click fired before React had finished hydrating the button, so it hit a plain DOM element with no
attached listener yet — visibility and the SSR'd `aria-disabled` attribute both resolve before
hydration, so the preceding assertions passed instantly and masked the timing gap. Every other
interactive test already in this file (`gotoWard`'s helper, the officer tests) already waits for
`networkidle` before its first click; my five added tests did not. Fixed by adding
`await page.waitForLoadState("networkidle");` after each visibility check (all five, for
consistency, though only the handover test strictly needed it — the other four are read-only
against static server-rendered attributes). This is a **mistimed test**, not an untestable
assertion and not a product bug — confirmed by the fact the identical assertion passes reliably
once the wait is added, with nothing else changed.

Separately, my "names transport, not examination" test's second assertion originally expected
`/Not yet requested/` for `WF-016` post-click; the real (correct) behaviour is `"Requested"`,
because `HANDOVER_READY` writes a brand-new `transport` object with no timestamps at all, and
`transportLeg` resolves that to the `"Requested"` leg, never `undefined` (`undefined` is reserved
for a movement with no `transport` object at all — e.g. `WF-319`'s fixture-authored
`handover_ready` state with no transport). Fixed the assertion to match the real, correct output.
